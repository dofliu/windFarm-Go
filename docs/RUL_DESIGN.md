# 每機獨立健康度 / RUL 預測性維護 — 設計草案

> 狀態:**設計草案(尚未實作)**。對應 [ROADMAP.md](ROADMAP.md)「後續接續工作」P2 教學深化項目、[GAME_DESIGN.md](GAME_DESIGN.md) §14 項目 5「機組健康度(Health Index)」文末預留的「後續可加:每機獨立健康度、付費進階檢測」,以及 §16 `#81` 明確點名尚未補齊的「狀態式 CBM(Condition-Based Monitoring)」這一類維護。本文只定範圍與資料模型,**不含程式改動**;實作將依下方「分階段實作計畫」逐輪推進,每輪一個明確階段。最後更新:2026-09-24(例行開發 session)。

## 1. 為什麼要做(現況缺口)

查核 `src/state/game.ts`/`events.ts`/`incidents.ts` 後確認兩件事同時成立:

1. **健康度是全場單一純量,不是每機的**:`fleetHealth`(`game.ts:240`,0-100)每日固定衰退 0.5(主線任務進行中未修復再 +1.5),由 `REST`/`REMOTE_CHECK`/`FINISH_REPAIR`/`SCHEDULED_SERVICE`/`OPS_INSPECT` 等動作回補。它只回饋到「今天要不要多丟一次故障事件」與「壞事件機率」這兩個全場層級的機率,**與個別機組無關**。
2. **機組個體模型已存在,但完全沒有劣化欄位**:`Turbine`(`game.ts:50-56`,Phase C 活體戰情層)已經有 `id`/`farm`/`status`/`faultId`/`gen`,工單 `OpsJob.turbine` 也已綁定具體機組 id(`game.ts:60`)——換言之「故障掛在哪台機組上」這個資料骨架已齊全,缺的只是「這台機組本身劣化到什麼程度」。目前「誰會故障」(`faultTurbines`、戰情室逐日新故障選取,`game.ts:608-619`)是**均勻隨機**挑一台正常機組,不吃任何機組個別歷史。

換句話說,現在的系統只能回答「今天整個風場運氣如何」,答不出「CH-07 這台快不行了,該排它優先定檢」——而這正是 CBM/預測性維護教學的核心情境判斷:**用趨勢資料預測哪一台、哪個部件會先壞,提前安排維護,而不是等故障發生再搶修**。§16 `#81` 已經承認現有 `diagLevel` 進階檢測只是「趨勢圖投影虛線+門檻線」的視覺判讀輔助,並未真正驅動故障率——本設計的目標就是把這個視覺敘事(「約 N 步後達門檻」「胞 ETA」)接上真正的數值模型。

## 2. 設計目標與非目標

**目標**
- 每台機組(`Turbine`)有自己的健康度/劣化狀態,可累積、可查詢、隨時間變化。
- 劣化程度影響「這台機組」個別的故障機率與故障嚴重度傾向,取代目前的均勻隨機挑選。
- 提供「剩餘壽命(RUL)」的粗略預估敘事,讓玩家能依預測結果排優先序做預防性維護,呼應真實 CBM 教學情境。
- 與既有機制整合,不另起爐灶:沿用 `OPS_INSPECT`(定檢)、`SCHEDULED_SERVICE`(計畫性保養)、`diagLevel`(付費進階檢測)作為「查看/延緩劣化」的既有操作介面。

**非目標(本輪不做)**
- 不做逐部件(齒輪箱/軸承/葉片…)各自獨立的多維度劣化模型——先用「每機單一劣化值」驗證核心迴圈與教學效果,部件級細分留待後續評估(#overhaul 大修分支已有 `MAJOR_FAULTS` 大修概念,未來可能是自然銜接點,但這次不展開)。
- 不引入新的貨幣/資源系統。
- 不改動雲端存檔格式的**必要**欄位(新欄位需可選、向後相容,見第 6 節)。

## 3. 資料模型草案

延伸 `Turbine`(`game.ts:50-56`),新增兩個欄位(皆為選配 `?:`,向後相容舊存檔):

```ts
export interface Turbine {
  id: string;
  farm: number;
  status: TurbineStatus;
  faultId?: string;
  gen: number;
  wear?: number;   // 新增:累積劣化度 0-100(0=全新,100=極高故障風險),預設 0
  age?: number;     // 新增:自建置/上次大修以來的累積運轉天數,預設 0
}
```

`wear` 是驅動故障傾向的核心量;`age` 是敘事/顯示用的輔助量(用於 RUL 預估文案的「已運轉 N 天」)。刻意不引入「剩餘壽命天數」這種精確倒數欄位——真實 RUL 預測本就有不確定性,若做成精確倒數會失去教學上「預測有誤差、需綜合判斷」的味道,改用第 5 節的「風險分級敘事」呈現。

**每日累積規則(草案,實作時再依 `npm run sim` 校正數值)**:
- 每日 `wear += WEAR_PER_DAY_BASE`(基礎緩慢累積,量級參考現有 `vesselWear` 每趟出勤累積、`SERVICE_VESSEL` 可歸零的既有手感)。
- 機組處於 `status==="fault"` 且未修復的天數,`wear` 額外加速累積(呼應 `fleetHealth` 現有「未修故障加速衰退」的既定敘事,`game.ts:550-553`)。
- `OPS_INSPECT`(定檢)、`SCHEDULED_SERVICE`(計畫性保養)完工時,對「被服務到的機組」(定檢目前是 `__sweep__` 全場性動作,見下方第 4 節整合建議)`wear` 打折或歸零一部分,而不是只補全場 `fleetHealth`。
- `FINISH_REPAIR`(完成維修)後,該機組 `wear` 大幅下降(等同「這次修好連帶把劣化也處理掉一部分」),但不歸零(呼應真實運維「修復不等於整新如新」)。

## 4. 與既有機制的整合點

1. **故障挑選改為加權而非均勻隨機**:`faultTurbines`(`game.ts:151-170`)與戰情室逐日新故障選取(`game.ts:608-619` 的 `oks[Math.floor(Math.random() * oks.length)]`)改成依 `wear` 加權抽樣(`wear` 越高,被抽中機率越高),但**保留下限機率**讓低 `wear` 機組仍有機會故障(真實世界也會有意外/隨機失效,不應讓「顧好高風險機組」變成絕對安全)。
2. **`OPS_INSPECT`(定檢)從「全場性」細化為「可選機組」**:目前 `OpsJob{kind:"inspect", turbine:"__sweep__"}` 是全場性動作(`game.ts:923-932`)。本設計建議**保留全場定檢**(維持現有教學節奏、免破壞既有存檔/測試),另外新增「針對單一高 `wear` 機組」的定檢選項,對該機組 `wear` 給更大幅折減——這給玩家「用診斷資料鎖定該巡哪一台」的具體決策點,是本功能教學價值的核心。
3. **`diagLevel` 付費進階檢測接上真數值**:自由營運中心 `TaskChart`(`OpsCenterModal.tsx`)目前的「約 N 步後達門檻」「胞 ETA」是視覺投影,不對應任何真實會被讀取的數值。解鎖 `diagLevel` 後,改為額外顯示該機組(或該次故障對應機組)的 `wear` 與粗略 RUL 分級(見第 5 節),讓付費檢測真正「看得更準」,而不只是「看起來更清楚」。
4. **`fleetHealth` 全場純量保留,新增 `wear` 平行存在,不互相取代**:`fleetHealth` 繼續驅動「今天壞事件機率」等全場性敘事(改動風險低、不影響既有測試/平衡);`wear` 只負責「壞事件挑中哪一台」與 CBM 敘事。兩條資料路徑刻意不耦合過深,降低一次性改動的回歸風險。
5. **主線任務 `TaskInstance.unit`(`tasks.ts:791`)與戰情室 `fleet[].id` 是兩套獨立編號**——研究已確認這個既有不一致點。本設計**不強行打通**(主線任務本就是獨立敘事,不需要真的對應 `fleet` 陣列狀態),但實作時需在程式碼註解明確記下這個邊界,避免未來誤以為兩者已同步。

## 5. RUL 呈現方式(教學敘事,非精確倒數)

依 `wear` 分四級(門檻待 `npm run sim` 時依實際分布微調),語彙延續現有「胞 ETA」「約 N 步後達門檻」的既有 UI 敘事:

| `wear` 區間 | 風險分級 | 敘事文案方向 |
|---|---|---|
| 0–29 | 良好 | 「劣化輕微,近期無需特別關注」 |
| 30–54 | 觀察中 | 「劣化趨勢上升,建議排入下次定檢」 |
| 55–79 | 高風險 | 「劣化明顯,建議優先安排維護,拖延故障機率顯著上升」 |
| 80–100 | 危急 | 「劣化嚴重,隨時可能故障,強烈建議立即處理」 |

顯示位置建議:母港機組列表(若戰情室 UI 有逐機列表可附加小型風險徽章)、`OpsCenterModal` 的機組相關面板、`diagLevel` 解鎖後的 `TaskChart`。**不在未解鎖 `diagLevel` 前顯示精確數字**,維持「進階檢測才看得清楚」的既有經濟誘因(呼應現有 `DIAG_COST` 設計)。

## 6. 存檔相容性

比照既有 `migrateSave`/`migrateVessels`(`game.ts:110-126`)的既有先例:`Turbine.wear`/`Turbine.age` 皆為選配欄位,讀取時 `t.wear ?? 0`/`t.age ?? 0` 補上預設值,不需要專門的遷移函式改寫舊存檔陣列本身,只在讀取端做防呆。雲端存檔摘要(`masterySummary` 先例)這次不需要新增欄位——`wear` 屬於單機局內狀態,不是跨帳號需要比較的統計量。

## 7. 平衡與測試計畫(留給實作階段)

- `test/run.mjs` 依既有分節慣例(見檔案內「戰情室:派工 / 遠端重啟」等分節)新增一段「機組個別劣化 / RUL」,至少涵蓋:`wear` 每日遞增不變式(0-100 夾界)、故障加速累積、`OPS_INSPECT`/`SCHEDULED_SERVICE`/`FINISH_REPAIR` 對 `wear` 的下修效果、加權抽樣在極端情況(全場 `wear` 相同)退化為近似均勻分布(避免破壞既有測試對隨機挑選機組的既有假設)。

## 8. 分階段實作計畫

不在單一 PR 內做完,依風險由低到高分階段:

1. **Stage 1・資料骨架 + 純展示(免影響平衡)**:`Turbine` 新增 `wear`/`age` 欄位與每日累積邏輯,母港/戰情室 UI 顯示風險分級徽章,但**故障挑選仍維持均勻隨機**(`wear` 純觀察用)。目的:先驗證資料模型與 UI 呈現、跑過一輪 `npm test`/`npm run e2e` 確認無回歸,不動平衡數字。
2. **Stage 2・接上故障挑選權重**:`faultTurbines`/戰情室逐日新故障選取改為依 `wear` 加權,`OPS_INSPECT`/`SCHEDULED_SERVICE`/`FINISH_REPAIR` 對 `wear` 的下修效果同步上線。此階段需要 `npm run sim` 重新校正。
3. **Stage 3・單機定檢動作 + `diagLevel` 真數值接軌**:新增「針對單一機組」的定檢/進階檢測選項,`TaskChart` 的 ETA 敘事接上真實 `wear`/風險分級。
4. **Stage 4(選配,依課堂回饋再評估)**:部件級細分、與 `#overhaul` 大修分支(`MAJOR_FAULTS`)的劣化觸發條件整合、教師端統計(如「班級平均機組劣化」)。

每個 Stage 各自是一個可獨立合併、可獨立回測的 PR,對應例行排程「大型項目拆階段推進,每次實作一個明確階段」的既定節奏。**下一輪例行開發建議直接從 Stage 1 開始實作**(資料骨架 + 純展示,風險最低、最適合先手)。
